# GOL-01：业务目标生命周期

GOL-01 将“事件被处理”与“用户目标已完成”分开。事件回执只能作为观察
输入；目标只有在显式成功条件满足后才进入 `completed`。

状态：**已提供可选 SQLite 持久化和 HTTP/回执接线，默认关闭，尚未部署验证**。
2026-09-25 先修复内存 ledger 的可靠性，再接入服务器回执、目标登记与重启恢复。
现已接入限定范围的只读文件哈希验证器、目标证据图谱，以及可选 Episode 到目标
的耐久通知 outbox；世界/记忆/外部行动的跨组件事务仍未接入。

## 启用与使用

设置 `EVA_ENABLE_BUSINESS_GOALS=true` 并重启服务；仅支持 SQLite，使用已有
`EVA_DB_PATH`。该开关独立于消费者选择，已对 legacy 和 Minimal 两种运行模式
做隔离 HTTP 测试。当前运行实例和 `.env.cloudflare` 未在本轮改动。

1. 调用 `POST /api/chat`，取得服务器生成的 `task_id`。
2. 调用 `POST /api/goals`，提供 `task_id`、description 和 success_conditions。
3. 使用 `GET /api/goals/{goal_id}` 或 `GET /api/goals/by-task/{task_id}` 查询。
4. 取消跟踪用 `POST /api/goals/{goal_id}/cancel`，传 `expected_version`。
   取消目标不会取消、撤销或重试原请求的动作。

创建示例（沿用 API 的身份认证）：

```json
{
  "task_id": "从聊天接纳响应取得",
  "description": "确认项目通过约定的只读检查",
  "success_conditions": [{"field": "checks.ready", "operator": "equals", "expected": true}]
}
```

一个 task_id 只能绑定一个目标；已过期而不在结果登记表里的请求不能新建绑定。
客户端不能提供 source_event_id、观察、证据或完成状态；字段从服务器登记记录取得。
条件字段限制为 `checks.*`（最多 16 条），不能拿 `receipt.ok` 当业务成功条件。
无 verification 清单的既有目标继续保存条件，不支持临时提交观察来完成。
新建目标可选择下述文件检查器；只有指定文件的服务器实测哈希全部匹配才完成。

## 只读文件验证器

`workspace_files_sha256_v1` 验证预先指定文件的字节内容是否匹配 SHA-256。
创建目标时同时传入固定 verification 清单，以及唯一成功条件
`checks.files_match equals true`。不允许把条件写成 false、数值 1 或其他字段。
预期哈希须由目标制定者给出；服务不会先读取当前文件来自动生成“期望”。

```json
{
  "task_id": "从聊天接纳响应取得",
  "description": "确认 artifact.txt 是约定的空文件",
  "success_conditions": [{"field": "checks.files_match", "operator": "equals", "expected": true}],
  "verification": {
    "kind": "workspace_files_sha256_v1",
    "files": [{"path": "artifact.txt", "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"}]
  }
}
```

请求已成功处理、目标为 pending_verification 后，调用
`POST /api/goals/{goal_id}/verify`，请求体只有 `{"expected_version": 3}`（以实际
查询到的版本为准）。路径、哈希和检查结果不能在这一步替换。接口使用原有身份认证。
若登记表在请求间更新了目标，版本冲突返回 409，需要重新读取目标再决定是否检查。

服务在 `EVA_BASE_DIR` 内读取最多 16 个普通文件，每个最多 2 MiB、每次读取 64 KiB。
只接受正斜杠分隔的相对路径；拒绝绝对路径、父目录、隐藏路径、Windows 设备名、
ADS、符号链接及 reparse point。检查打开前后身份、长度、mtime/ctime；检测到变动、
读取错误或大小超限时返回 unknown，不升级为完成。它不会执行脚本、运行测试、
访问网络或返回文件内容。字节预算不等于硬实时期限；慢文件系统可能延迟返回。

匹配结果为 passed，目标 completed；缺失或哈希不同为 mismatch，仍保持
pending_verification；无法读取为 unknown，也保持待验证。文件变化后可用新版本
再次检查未完成目标，历史尝试会保留。终态目标不重开；完成意味着本次指定字节检查
通过，**不等于代码功能正确，也不证明这些文件由关联聊天请求生成**。

这是带时间的逐文件采样（scope=file_content_samples），不是全工作目录原子快照，
也不保证文件随后不变。每个结果包含 observed_at，整次检查记录 started_at 和
结束 observed_at。文件系统检查假设工作目录不被恶意并发替换；不是 OS 沙箱边界。

读取文件在数据库锁之外执行，完成后再次核对目标版本、源事件和不可变清单。
目标版本变化、取消或检查期间到期会拒绝提交；检查结果与目标状态在同一事务保存。
结果包含 run_id、检查器版本、目标/源事件 ID、提交前后目标版本、预期与实测哈希。
失败的 SQL 提交不留下半条完成状态。不会将文件哈希伪装成世界图的 state_revision。

重启恢复为 interrupted 的目标，仅在已经持久化 succeeded 处理回执时允许显式再次
读取文件；unknown/failed 执行不能被文件存在性反推为成功。检查不会重放原动作。
新增的 business_goal_verification_specs 与 business_goal_verifications 表通过幂等
建表附加到已有数据库；未带清单的历史目标不自动迁移为可验证目标。

## 目标与检查图谱（2026-09-27）

完整服务首页左侧“数据视图 → 目标与检查”读取 `GET /api/goals/graph`。
功能沿用业务目标开关和 API 认证；未启用返回 503，界面显示不可用并允许切回记忆。
独立 memory_preview 不构造目标服务，禁用此选项。

- G：业务目标，展示已存状态、版本、成功条件、截止时间和固定检查清单。
- R：请求回执，明确区分“请求已处理”和“目标已验证”；不补造回执时间。
- V：文件检查，展示通过 / 不匹配 / 未知、采样时间、目标版本与逐文件预期/实测哈希。
- E：已有 Episode 执行记录，按来源事件严格匹配，展示状态 revision 或无版本世界快照哈希、已知策略/规划版本与动作回执引用。

连线仅依据同一 goal_id 的回执与检查引用，类别为 `goal_evidence`，不推断因果关系，
不将这些记录冒充 S1–S5 记忆。仍支持粒子效果、缩放、节点点击、类别筛选和局部路径。
原记忆图谱与 Obsidian 导出保持记忆范围；目标视图不提供笔记导出。
目标详情可显式发起版本保护的“重新检查指定文件”或“取消跟踪目标”操作。两种操作都需要用户
点击，使用当前目标版本号；成功后刷新证据图谱，409 版本冲突不会被页面自动重试，也不会把
请求回执直接提升为目标完成。已完成、失败、取消和过期目标不显示可写操作。

接口接受 limit（默认/上限 40）、offset（默认 0）和 q（最多 200 字符，匹配描述或
目标/请求/事件 ID）。按登记顺序倒序分页，每目标最近 5 次检查，最多 320 节点、
280 条引用（含每目标最多一个已有 Episode）；目标详情显示完整检查次数，超限明确标为部分历史。页间新登记可能导致
边界移动，不保证跨请求分页快照。计数为本页记录数，匹配目标总数另列。

选中目标后可读取 `GET /api/goals/{goal_id}/history?limit=20&offset=5` 获取较早的
文件检查记录（limit 上限 50，按目标版本倒序）。该接口只读同一 SQLite 快照，返回
`read_only=true`、`total` 和 `next_offset`，不调用 `get()`、不对账、不推进目标、不读取
文件；历史记录仍是采样证据，不代表当前文件状态。

一次请求使用同一 SQLite 读事务，`Cache-Control: no-store`；不调用可写 get()、
不对账、不恢复、不推进过期状态、不触发文件检查。故到期但尚未推进的目标可能仍
显示已存 active/pending 状态，详情同时显示截止时间和快照说明。已通过检查仍是历史
证据，不宣称当前文件未变化。界面不会通过刷新自动执行 verify。

执行记录接线参见 [EPI-01](episode-records-epi01.md)。`GET /api/goals/{goal_id}/episode`
为只读引用接口，不调用对账 get()。Episode 必须存在于同一 EVA 数据库；表不存在、
来源事件未记录、格式/身份异常分别标注，异常不绘制引用节点。每条原记录限 64 KiB，
仅投影最多 16 个动作的 ID、类别、状态与回执引用及有界版本信息。另行启用
`EVA_ENABLE_PROCESSING_EPISODES=true` 后，共享处理器写入草稿并按首个终态封存，
重启优先核对已持久化的服务器回执，没有可靠回执则将未封存处理标记为未知，
不重放动作。封存事务同时保存终态摘要和目标通知，通知失败可幂等补送；目标
读取/对账在内存回执缺失后可读取摘要，图谱/历史/引用接口仍不对账。默认仍关闭，
草稿不绘制节点，不能宣称所有目标都有执行追溯。线程内注册工具/Executor 的
开始、返回与中断收据已接入 Episode 引用，工具未知结果不能当作业务失败或成功；
世界/记忆/行动跨组件事务、未覆盖执行入口和远程结果对账仍待开发。新目标登记
仍要求当前进程的已登记请求，不由摘要恢复聊天正文。

## 目标登记表单（2026-10-01）

完整服务的“目标与检查”视图提供“登记目标”对话框，使用现有 `POST /api/goals`。
填写已登记请求的 task_id、目标描述、可选截止时间，以及 1–16 行
`相对路径 | SHA-256`。截止时间按当前设备时区转换为带时区 UTC；文件清单在服务器
登记后不可变，唯一完成条件为 `checks.files_match equals true`。不会从当前文件生成
期望哈希，也不会自动执行任务或检查文件。路径与清单最终以服务端验证为准。

提交期间锁定字段，关闭再打开对话框不会中止或重发提交。网络错误、超时、409、503
或无法确认响应时，保留当前请求 ID，锁定再次提交，要求用户显式“查询登记结果”。
查询使用 `GET /api/goals/by-task/{task_id}`，可能补记回执与推进过期状态；它不是图谱的
只读投影接口。找到目标后展示服务器原记录，不替换成表单草稿；查询 404 后才允许
显式修改或再次提交，服务器仍拒绝重复绑定。重载页面后应使用原请求 ID 先查询，
草稿和提交锁仅保留在当前页面内存中；关闭对话框保留草稿，“登记另一个目标”显式清空。

成功登记或查询到已有目标后，按目标 ID 刷新图谱并选择真实返回节点；图谱读取失败
不会抹掉对话框中的登记结果，可再次“在图谱中查看”。不会补造节点或将登记标为完成。
独立只读预览禁用入口且不加载登记脚本。默认业务目标开关仍关闭。

## 回执与事务边界

ResultRegistry 的首次终态通知持久化组件，涵盖执行结果、等待超时和停止时拒绝。
通知中的 task/event ID 来自接纳记录。模型生成的 reply、checks、review 声明不会
被用作业务证据，也不保存到目标的 processing_receipt 中。

| 请求终态 | 未到期 active 目标的状态 |
| --- | --- |
| succeeded | pending_verification |
| outcome_unknown | interrupted |
| failed / rejected | failed（执行未完成，不表示期望事实被证伪） |
| expired | expired |

取消、已到期或已中断的目标不会被迟到成功回执重新激活。重复的同一回执不增加
版本，冲突终态拒绝覆盖。没有业务检查结果时返回 `verification_state=not_verified`；
检查后返回最新历史结果 passed/mismatch/unknown 和 last_verification。

`business_goals` 和 `business_goal_receipts` 是同一 EVA 数据库的附加表，记录
schema_version=1。组件首次启用时以幂等 CREATE TABLE 建表；未知记录版本拒绝
恢复。每次用 `BEGIN IMMEDIATE` 读取当前版本、更新目标并写回执，失败整体回滚；
不依赖进程内缓存充当持久权威。已有数据库启动迁移流程不转换历史目标快照。

**聊天接纳、内存结果登记和目标事务不是同一个事务。** 回执观察器写库失败时，
聊天结果继续保留，`receipt_observer_errors` 在当前进程内累计错误；目标查询会从尚在保留期内
的权威回执补记。创建目标前后读取登记表以覆盖登记竞态。如果补记前进程崩溃或
回执保留期结束，未保存的回执可能丢失；目标重启后变为 interrupted，不猜测完成。
这不提供持久聊天接纳、通用 exactly-once 或自动对账。

观察器同步执行，SQLite 等锁最多等待配置在组件内的 2 秒，因此该可选功能可能
增加请求完成延迟。目标组件不调用回执登记表，避免反向锁依赖。仍只支持一个
应用进程，恢复操作必须在启动消费者前执行，不能当作多实例领导权协议。

`/api/runtime` 的 `extensions.business_goals` 和 `/api/config` 报告挂载状态、
观察器累计错误和 business_verifier_attached；启用功能后文件验证器随组件挂载，
不把已挂载表述为已验证目标。

## 生命周期

目标状态包括 `queued`、`active`、`pending_verification`、`completed`、
`failed`、`cancelled`、`interrupted` 和 `expired`。状态转换带版本号，旧版本
提交会被拒绝。目标依赖必须先完成，才能激活后续目标。

新目标只能以 `queued`、version 1 创建，不能通过 `create` 预设为完成，
也不能通过 `transition(..., "completed")` 绕过条件。已有终态只能从可信
快照恢复。自依赖会拒绝；跨目标依赖环检测尚未实现。

读取、版本检查和提交使用同一进程内锁。需要防止覆盖的调用方必须传
`expected_version`；省略时只保证串行提交，不提供调用方版本冲突检测。
输入验证失败不改变状态、版本、观察或证据；批量恢复全部验证后才提交。

## 成功与失败

`GoalCriterion` 支持确定性的字段谓词：`equals`、`not_equals`、`contains`、
`gte`、`lte` 和 `truthy`。观察先检查失败条件，再检查全部成功条件；条件
不完整时进入 `pending_verification`。已记录状态 revision 后，后续观察必须
带相同或更高 revision，避免旧观察或无版本观察覆盖新状态。

**谓词匹配不等于事实核验。** `observe` 接收调用方提供的字典，ledger 本身
无法判断它来自真实工具还是模型生成。`evidence` 仅为附带记录，不是可信认证。
后续业务检查器必须从受控检查取得观察并核对来源，不能把任意模型输出或
HTTP 请求内容直接视为完成证据。`restore` 同样只应接收可信内部快照，
不对历史 `completed` 记录重新证明成功。

## 截止时间

时间字段必须带时区；默认时钟使用 UTC，也可注入时钟进行确定性测试。
达到 deadline 的非终态目标拒绝激活、观察和一般状态推进，仍可取消。
所有者显式调用 `expire_due()` 将到期目标转为 `expired`，每个目标只增加
一次版本；该函数没有后台定时器。读取不会触发过期写入。

## 重启与边界

恢复时，到期的非终态目标转为 `expired`；尚未到期的 active/pending 目标
变为 `interrupted`，需要新的激活动作，queued 保留排队状态。历史终态保持
原样。恢复不执行工具、不重放动作。观察、证据和恢复输入会复制保存，
防止调用方事后修改 ledger。数据库事务内加载当前行使用 `restore(recover=False)`，
不把每次读写当作重启；启动时单独调用 store.recover() 原子恢复整批记录。
应用构造失败和有序停机都会关闭组件连接；工作线程结束前保留依赖。

兼容性：旧的无时区时间、布尔或非整数版本会被拒绝；失败的恢复不写入任何
记录。升级前应在数据库/快照副本上验证并备份；不能替旧数据猜测时区。本轮仅在
测试临时目录演练持久化，没有修改运行数据。回退可关闭功能开关后重启，保留附加
表供重新启用；如果回退整个数据库，应使用受控备份恢复流程，不能直接删除表。
