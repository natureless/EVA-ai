- JavaScript 数量来自仓库当前 `tests/js` 集合，包含界面之外的客户端模块；34 项 Python 是交付检查与记忆图谱子集，不是全后端测试或模型能力评估。
- [设计适配与后续证据](ui-openai-adaptation.md)：七页主题布局、60 组导航、12 组配置审阅、字号模拟、交付竞态与失败保留。矩阵与截图分别证明自身范围，不把历史矩阵当成每个新增状态都已通过。
- [性能观测](ui-logo-perf01-observations.md)：已有十分钟三阶观测和资源采样，但内置浏览器存在宿主节流；不能据此承诺前台帧率、无泄漏或通过性能门槛。

发布检查仍明确保留四项待验收：原生 Chrome／Edge 保存与直接离线执行、可靠前台双阶各十分钟性能、原生 200% 缩放、真实屏幕阅读器。真实手机软键盘与服务联调另纳入以下计划。

## 复盘结论

有效的设计与工程选择应继续保留：真实魔方状态与呈现分离，统一几何派生资产；正常／深度模式随请求固定；未知结果只查询原请求；全界面主题共享但不改变 Logo 几何；错误恢复保留日志与草稿；报告绑定具体版本和源码指纹。这些形成了当前系统的维护基础。

下一阶段需要解决三个收敛问题。其一，连续的小改动增加了体验完整度，但原生和实机门槛长期未关闭，开发投入应转向验收。其二，计划与验收文档分散且带有历史数字，需使用一份最新状态表，专项文件保留原始证据。其三，当前工作树混有大量后端与 UI 变更，且品牌工作区与星图脚本承担多类职责；交付前需要明确文件和契约边界，后续按实际改动拆分职责，避免一次重写。

不把代码行数当成缺陷或强制拆分理由。优先抽取反复变更的配置审阅、导出反馈、详情面板等边界，保留可独立验证的状态契约。
