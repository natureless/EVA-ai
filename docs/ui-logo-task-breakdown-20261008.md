## 第一批与依赖顺序

第一批只做 **G0-01 → G0-02 → G0-03 → G0-04**，预计 4–8 小时。交付候选基线、界面状态清单、接口依赖清单与验收工作单，再进入原生与服务验收。当前原生连接状态未知，G1-01 到时只做一次有目的的环境核验；不可用则记录未验证与具体原因，先推进可执行的服务联调和整理工作。

| 顺序 | 开始条件 | 完成后可进入 |
| --- | --- | --- |
| G0 基线与清单 | 已有源码、历史证据 | G1 原生验收、G2 服务联调 |
| G1 原生与实机 | G0-04；对应浏览器／设备可操作 | 下载／离线、缩放、辅助技术、手机专项；各项独立记录 |
| G2 服务与状态 | G0-04；隔离环境与测试数据可用 | 对话、图谱子面板、运行信息专项 |
| G3 性能 | 原生环境可操作；核心联调已记录；已发现的前置 P0 缺陷关闭；候选源码稳定 | 双阶长测与设备基线 |
| G4 修复与整理 | 已有明确缺陷或重复维护问题 | 对受影响调用端复验；必要时重测 G3 |
| G5 最终候选 | G1–G3 必要项通过、P0 缺陷关闭；P1 延期说明齐全 | 最终自动检查、包内容与同版人工证据对账 |

G1 与 G2 的独立项可在环境空档穿插安排；本估算仍按一名开发者执行，不假定多人同时工作。任一性能／组件修复后，重测受影响的性能场景，不能把修复前记录绑定到修复后的候选。

## 工作单状态与证据格式

| 状态 | 使用条件 |
| --- | --- |
| 待执行 | 有任务定义，尚未开始 |
| 进行中 | 已开始，记录当前步骤和依赖 |
| 通过 | 验收条件满足，环境与同版证据齐全 |
| 失败 | 已执行但条件不满足，关联缺陷及修复任务 |
| 未验证 | 环境、设备或依赖不可用，记录具体原因；不可计为通过 |
| 延期 | 仅用于 P1 或明确缩小范围后的项目，说明影响及返回条件；P0 保持门槛未通过 |

后续每项实际执行记录至少包含：`taskId`、状态、起止时间、候选源码指纹、版本、环境、前置条件、步骤、预期与实际结果、证据路径、缺陷／复验关联。候选目录可采用 `artifacts/ui-acceptance/<candidate>/<taskId>/`。G0 已有采集与结束时间，人工开始时间未记录，保留 null；不把估算工时写成实际耗时。G1–G5 未创建通过占位记录。

截图证明呈现，网络记录证明请求，状态快照证明魔方逻辑，实际落盘文件证明保存；证据类型不能互相替代。测试注入、临时字号、媒体／视口模拟和观测器均需登记并清理。缺陷记录至少包含复现环境、影响工作流、优先级、修复来源和复验结果。

## 排期与工时汇总

| 阶段 | 任务数 | 工时 | 人日 |
| --- | --- | --- | --- |
| G0 | 4 | 4–8h | 0.5–1 |

基础排期按有效工作日推进：第 1 个半日至 1 日做 G0；随后优先验证原生环境并开始 G1／G2；环境空档执行独立联调项。核心问题关闭后做 G3，再完成维护收敛与 G5。发生 P0 缺陷时穿插 G4-01／04，受影响专项复验。另留 1–3 人日处理超预算兼容缺陷；环境等待不算有效工作日，不预设承诺完成日期。

第一批验收结果应能直接回答四件事：候选是什么版本；共有多少页面／子状态；哪些 API 操作会写入；哪些门槛当前没有证据。四项明确后，再按任务号开展下一批开发。
